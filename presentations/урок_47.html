  • 2
    Есть ли экран конца игры? — «Игра окончена» / «Ты победил» — явный экран, не просто остановка.
  • 3

  • 4
    Баланс звука? — Фоновая музыка тихая (0.3–0.5), эффекты чуть громче (0.6–0.8). Не пережигает уши.

Частые ошибки при полировке

Смотрим на реальный код и находим что улучшить

❌ Антипаттерны

  • x = 1; y = 2; z = 3 — магические числа
  • Функция из 80 строк, делает всё сразу
  • except: без типа ошибки
  • Переменная a, b, qq2 — непонятные имена
  • Один файл с 300+ строками без разделения

✓ Как правильно

  • SPEED = 5; MAX_HEALTH = 100 — константы
  • Одна функция = одна задача (SRP)
  • except ValueError as e: — конкретный тип
  • player_speed, enemy_count — говорящие имена
  • Разбивка на файлы: game.py, player.py, ui.py

Меню + перезапуск (state machine)

STATE = "menu"  # menu / play / gameover

def draw():
    screen.fill("black")
    if STATE == "menu":
        screen.draw.text("Нажми SPACE для старта",
            center=(400,300), fontsize=32,
            color="white")
    elif STATE == "play":
        draw_game()
    elif STATE == "gameover":
        screen.draw.text("Игра окончена! R = restart",
            center=(400,300), fontsize=32,
            color="red")

def on_key_down(key):
    global STATE
    if STATE == "menu" and key == keys.SPACE:
        STATE = "play"
        reset_game()
    elif STATE == "gameover" and key == keys.R:
        STATE = "menu"

Подсказка на экране (первые 3 сек)

hint_timer = 3.0  # секунды показа

def update(dt):
    global hint_timer
    if hint_timer > 0:
        hint_timer -= dt

def draw():
    screen.fill("black")
    draw_game()
    if hint_timer > 0:
        screen.draw.text(
            "Стрелки — движение, SPACE — прыжок",
            topleft=(10,10),
            fontsize=18, color="yellow",
            alpha=min(255, int(hint_timer*100))
        )

Шаг 3: Чини

По списку — от самого критичного. Краши и freeze → первыми. Косметика → последней

Приоритеты багов

  • Красный: Игра зависает или крашится — чинить немедленно
  • Оранжевый: Непонятно правило или объект телепортируется — чинить сейчас
  • Жёлтый: Мелкая графика не та — чинить если есть время
  • Зелёный: Хочу добавить фичу — в список «ideas», не сейчас
Правило «заморозки кода»: в день защиты код не трогаем. Лучше стабильная игра без новой фичи, чем падающая игра с ней.

Техника «Резиновой уточки»

Объясни баг вслух — и часто сам найдёшь решение

  1. Возьми любой баг из своего трекера
  2. Объясни его вслух — как будто учишь меня с нуля
  3. Говори каждую строку кода: «здесь я делаю X, потому что Y»
  4. В какой-то момент сам заметишь: «Стоп, вот где ошибка!»

Этот метод работает, потому что когда мы объясняем — мы думаем линейно и находим то, что пропустили глазами

Зачем это работает?

Мозг
переключается с «написать» на «объяснить»
Логика
становится линейной, а не параллельной
Ошибки
всплывают при словесном описании
У Amazon и Google разработчики используют «rubber duck debugging» официально

Хорошая vs плохая защита

Смотрим на реальные примеры — учимся на различиях

❌ Слабая защита

  • «Я сделал игру, вот она»
  • Читает код строка за строкой без объяснений
  • На вопрос «почему так?» отвечает «не знаю»
  • Говорит об ошибках с извинениями
  • Монотонно, тихо, не смотрит на слушателей

✓ Сильная защита

  • «Я создал игру X, потому что хотел Y»
  • Показывает функции: «вот здесь происходит…»
  • «Я выбрал словарь, потому что поиск быстрее»
  • «Была проблема с X — я решил её через Y»
  • Уверенно, смотрит на собеседника, улыбается
Хорошая защита — это рассказ о твоём мышлении, а не демонстрация кода

Словарь уверенного выступающего

Что говорить вместо типичных ошибок

Так не надо

  • «Я тупил и не понимал»
  • «Ну, в общем, игра такая, типа...»
  • «ИИ мне всё написал»
  • «Я не знаю, почему так работает»
  • «Проект плохой, я мало успел»

Говори так

  • «Столкнулся со сложностью и вот как решил»
  • «Моя игра — это... Цель игрока — ...»
  • «Kandinsky помог с картинками, код — мой»
  • «Здесь я применил коллизии из урока 39»
  • «За 48 уроков я сделал 11 проектов»
Главное правило публичного выступления: говори медленнее, чем думаешь нужно. Паузы — не враг, а инструмент.

Волноваться — нормально

Даже опытные программисты нервничают перед демо. Вот как это используют в свою пользу

Три техники

  1. Дыхание 4-7-8
    Вдох 4 сек → задержка 7 сек → выдох 8 сек. Повторить 3 раза. Снижает пульс.
  2. «Это не экзамен»
    Демо-день — это показ, а не оценка. Ты уже сделал игру — это факт, который не отнять.
  3. Маленькая защита дома
    Покажи игру маме/папе/другу. Первое выступление всегда самое сложное — пусть оно будет дома.

Если что-то пошло не так

  • Игра не запускается → запусти backup файл, скажи «бывает, вот запасной план»
  • Забыл что говорить → посмотри в defence.md, пауза — это нормально
  • Застрял на вопросе → «Хороший вопрос, я об этом не думал — займусь после»
  • Замёрзли руки → это адреналин, он помогает, сделай вдох и продолжай

Проверь себя: 5 вопросов

  1. Что такое «рефакторинг» и чем он отличается от исправления бага?
  2. Что значит «принцип единой ответственности» (SRP) для функции?
  3. Как работает техника «резиновой уточки»?
  4. Что должно быть в файле defence.md? Назови 3 раздела.
  5. Почему в день защиты нельзя добавлять новые фичи?

Ответы:

  1. Рефакторинг — улучшение структуры без изменения поведения. Баг-фикс меняет поведение.
  2. Функция делает одну вещь, несёт одну ответственность.
  3. Объясняешь баг вслух (уточке/другу) — мозг переключается и сам находит ошибку.
  4. Идея проекта + самый сложный момент + чем горжусь (+ любые другие разделы).
  5. Риск сломать стабильную игру ради фичи — лучше стабильная без новшества.

Словарь урока 47

Рефакторинг
улучшение структуры кода без изменения его поведения: лучше читаемость, проще поддержка
SRP
Single Responsibility Principle — принцип единой ответственности: одна функция делает одно дело
Rubber duck debugging
техника: объясняешь баг вслух — мозг переключается и сам находит ошибку
defence.md
файл с планом устной защиты проекта: идея → сложность → решение → чем горжусь
Code freeze
правило «заморозки»: за день до демо новый код не добавляется, только стабилизация
Полировка
финальный этап разработки: UX-детали, меню, перезапуск, понятные имена, удаление мусора
